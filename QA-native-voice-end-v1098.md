# v1098 — native completion and interrupted second captures

The supplied iPhone screenshot confirms production1097 and ERROR_ABORTED on the second capture. Two application event orders reproduced data loss: final → JavaScript stop → aborted → end, and speechend → stop → aborted → late final. The old error path also enabled another capture before native end.

Native speechend/final events are now passive for continuous=false. They retain the bounded closing state without another stop request. Explicit user stop and the capture watchdog may request stop once. Native errors retain ownership until end or bounded cleanup; confirmed final text may survive aborted, while other errors and interim-only text never enter financial fields. Draft/view identity and newer-manual-edit guards remain in force. No automatic recording restart was added. Diagnostic reasons use fixed categories and never retain raw native messages.

An error-only command panel also accepts typing or the keyboard's own dictation. Text does not change the form until the user explicitly applies it through the existing parser. Active/closing native captures block application. Commands are bound to the draft, escaped in HTML, and protect navigation/update reload before application. Nothing automatically saves a transaction, starts recording, or uploads audio through this panel.

Tests cover native error/final ordering, second taps before end, fatal-error latching, sanitized reasons, timeout, cancellation, manual edits, repeated corrections, keyboard command apply/undo, stale drafts and pending-command protection. Browser tests exercise both routes at six widths with isolated synthetic data. The existing QA fixture's default project end date is now relative, so an unrelated calendar rollover cannot create an urgent-project alert in transaction-only tests. Source/cache identity is1098; storage keys, APP_RELEASE800, accounting calculations and backend contracts are unchanged.

Primary research: [WebKit native task implementation](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/Modules/speech/cocoa/WebSpeechRecognizerTask.mm#L205-L234) stops native single-shot recognition after its final and can send aborted before end. [WebKit report321436 comment3](https://bugs.webkit.org/show_bug.cgi?id=321436#c3) separately describes second-capture failure. Those current upstream sources may differ from this phone; they do not establish its exact native cause.

All automated audio events and keyboard input are synthetic. Actual iPhone Safari/PWA microphone and keyboard dictation remain device checks. The change fixes demonstrated application races and provides an explicit fallback; it does not claim to repair every platform audio failure. Real customer Sheets and backup data are not used by these regressions.
