# AREA Ledger v1043 — BOQ provenance and release evidence

## Changes

- Preserve identical BOQ items on different pages/files through quality filtering, AI coverage and reconciliation. Same-page duplicate OCR evidence still collapses.
- Bind physical iPhone acceptance to the deployed commit, environment and build version. Each check expires independently after seven days; rechecking one item cannot refresh the others. Failed persistence restores prior evidence.
- Run the approved real Pr.4 image against Gemini after staging and production live acceptance. Require four material/labor rows, exact printed quantity, unit prices, amounts and section 1.2.2. Store fixture hash and deployed build with the result. An HTTP 200 alone cannot pass.
- Run provenance and verifier regressions in all release pipelines. Correct the QA preflight YAML so legacy-app regression actually runs. Normalize CRLF in three existing CSS source tests for Windows portability.

Upright-only OCR, progress, review-before-save and explicit save remain enforced by existing regressions. Storage format and accounting release v800 remain unchanged.

## Validation and limits

Local validation covers 29 CommonJS suites (including 552 main QA groups), the document verifier contract and script syntax. The actual Pr.4 test passed against staging v1042 commit 3b08d4eb6c034e3ea80daf12a8bc351c810c468e on 2026-10-04; this is baseline evidence, not acceptance for v1043. Candidate deployment evidence is generated by Actions after publication.

This fixture is a regression sentinel and is represented in the provider prompt. Passing it is not an independent accuracy benchmark. Physical iPhone checks require a real device and are not asserted by Node tests.

## Next readiness milestones

1. Build a consented, held-out document benchmark across contractors, poor scans, multi-page tables, handwritten annotations and mixed Thai/English. Measure field accuracy, missing rows, false rows and correction time separately.
2. Review authentication, tenant isolation and role enforcement server-side; exercise restore and concurrent-edit conflicts with independent accounts before multi-company expansion.
3. Measure OCR latency, error rates, recovery and costs under realistic load; establish operational targets from measured traffic and run restore drills.
4. Test real iPhone/Android and keyboard/screen-reader workflows, including offline recovery and failed uploads.
5. Scope localization, currencies and jurisdiction-specific accounting/tax with explicit supported-country requirements. The current Thai workflows do not establish international compliance.

These are release milestones, not a claim of global readiness.
